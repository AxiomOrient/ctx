# ctx 개발 워크플로우: `compose_prompt`

**마지막 업데이트: 2025-08-30**

## 1. 개요

`ctx`는 복잡한 계획 관리 도구가 아니며, 핵심 기능은 **결정론적 프롬프트 생성**에 집중되어 있습니다. 이 문서는 `ctx`의 가장 대표적인 워크플로우인 `compose_prompt`가 Tauri 데스크톱 UI를 통해 어떻게 실행되는지 단계별로 설명하여, 시스템의 전체 아키텍처가 어떻게 상호작용하는지 보여줍니다.

## 2. UI 기반 프롬프트 생성 흐름

UI에서 사용자가 프롬프트를 입력하고 '생성' 버튼을 누르면, 다음과 같은 흐름으로 `ctx`의 모든 계층이 동작합니다.

1.  **`apps/ui` (프론트엔드)**
    - 사용자가 프롬프트 내용을 입력하고 'Generate' 버튼을 클릭합니다.
    - `RightDockPrompt.svelte`와 같은 Svelte 컴포넌트가 `lib/ipc.ts`에 정의된 `compose` 함수를 호출합니다.

2.  **`lib/ipc.ts` (IPC 래퍼)**
    - Tauri의 `invoke('compose', ...)` 함수를 호출하여 백엔드(Rust)의 `compose` 함수를 비동기적으로 요청합니다. 이 과정에서 프론트엔드와 백엔드 간의 데이터 타입은 TypeScript와 Rust에서 공유되어 타입 안정성을 보장합니다.

3.  **`app/ui/tauri_app.rs` (Tauri 핸들러)**
    - `#[tauri::command]` 어트리뷰트로 노출된 백엔드의 `compose` 함수가 IPC 요청을 수신합니다.
    - 수신된 요청은 실제 로직이 담긴 `app/ui/ipc.rs`의 `compose` 함수로 전달됩니다.

4.  **`app/ui/ipc.rs` (UI 백엔드 로직)**
    - IPC 요청의 파라미터를 검증하고, `services` 계층의 `compose_prompt` 함수를 호출하여 핵심 로직 실행을 위임합니다.

5.  **`services/mod.rs` (유스케이스 파사드)**
    - `compose_prompt` 함수는 `Pipeline` 객체를 생성하고, `config.toml` 설정과 `knowledge` 베이스를 로드합니다.
    - 준비된 `Pipeline` 객체의 `execute()` 메소드를 호출하여 본격적인 프롬프트 생성을 시작합니다.

6.  **`pipeline/mod.rs` (핵심 로직)**
    - **7단계 파이프라인**이 순차적으로 실행됩니다.
    - (정규화 → 분류 → 점수화 → 선택 → 트리밍 → 템플릿화 → 전송)
    - 이 과정에서 `domain`의 데이터 모델과 `drivers`의 외부 시스템 연동이 모두 사용됩니다.

7.  **결과 반환**
    - 파이프라인 실행이 완료되면, 생성된 `PromptBundle` 객체가 `services` → `app` → Tauri IPC 채널을 거쳐 프론트엔드로 안전하게 반환됩니다.
    - 프론트엔드는 반환된 결과를 받아 UI에 표시합니다.

이러한 흐름은 모든 의존성이 외부(UI)에서 내부(도메인)로 향하며, 각 계층이 명확한 책임을 갖는 전형적인 클린 아키텍처(Clean Architecture) 구조를 보여줍니다.
